# Stock EVA 策略级复盘平台 Roadmap

> 日期：2026-07-29
>
> 状态：Planning draft，待确认
>
> 范围：A 股盘后复盘、研究与仓位辅助；不包含实时行情、券商接入、自动下单
>
> 调研基线：`myhhub/stock@b6e0ca2`、`TradingAgents@a33fd4c`、`vnpy/vnpy@1b78494`

## 1. 结论摘要

推荐采用“保留现有后端，按能力模块适配复用”的路线：

- 保留现有 BaoStock → DuckDB/Parquet → FastAPI 数据链路、SQLite 用户数据、`as_of_date` 和无未来数据约束。
- 不整体迁移三个仓库中的任何一个。它们分别带有旧 Web/数据库栈、LLM 多代理运行时、桌面交易框架，与本项目的本地盘后 Web 产品边界不一致。
- 从 [InStock](https://github.com/myhhub/stock) 复用 A 股指标、形态、筹码与任务分类的领域设计；实际计算优先使用受控的 TA-Lib 适配层，并建立金标测试。
- 从 [TradingAgents](https://github.com/TauricResearch/TradingAgents) 复用“证据包 → 分角色分析 → 风险辩论 → 结构化结论 → 决策日志”的工作流设计，不在首期引入其完整 LLM 运行时。
- 从 [VeighNa](https://github.com/vnpy/vnpy) 复用指标注册、时点化成分股、因子研究和组合回测的设计；不引入交易网关、事件引擎和桌面 UI。
- Web K 线建议直接采用 [KLineChart](https://github.com/klinecharts/KLineChart)，技术指标建议基于 [TA-Lib Python](https://github.com/TA-Lib/ta-lib-python) 封装。本项目无需为基础金融图表和 150+ 常见指标重新造轮子。

产品北极星：

> 在收盘数据就绪后 5 分钟内，用可追溯的 `as_of` 数据完成“市场状态 → 资金证据 → 板块轮动与龙头 → 个股技术 → 仓位风险”的闭环复盘。

## 2. 当前状态与问题诊断

### 2.1 已经可用的基础

- 盘后数据服务已运行，当前交易日覆盖率可达完整状态。
- 已有指数、市场宽度、成交额、个股日线历史、持仓、自选、策略和提醒接口。
- 数据契约已经强调交易日、数据版本、`as_of_date`、暂停交易和质量状态。
- 当前指标 DSL 已支持 SMA、EMA、RSI、量比和交叉等基础表达。

### 2.2 真正缺失的不是“多画几张图”

当前页面价值低的根因是没有形成面向决策的派生数据产品：

1. 个股历史接口存在，但没有个股详情页、K 线或指标图。
2. 没有可靠的板块分类历史、板块状态、轮动和龙头模型。
3. 补充数据接口目前未配置，市场和板块资金流没有可发布记录。
4. 市场状态只有基础宽度和两个指数，无法支撑可信的全 A 股牛熊判断。
5. 没有把市场、板块、个股和持仓风险汇总成同一份证据链。
6. 当前股票池主要是沪深主板；扩展前不能把结果表述成“全 A 股市场”。

因此，路线图必须先补“派生分析层”，再升级页面；只改视觉会得到更漂亮但仍然无法决策的仪表盘。

## 3. 用户需要完成的五个决策任务

| 决策任务 | 平台必须给出的结果 | 不允许的做法 |
|---|---|---|
| 近期主力资金在做什么 | 多来源、多时间窗、带置信度的资金证据 | 用单日排行或成交额冒充真实资金流向 |
| 市场是牛、震荡还是熊 | 战略状态、战术风险偏好、证据和反例 | 只输出一个黑盒标签 |
| 强势板块和龙头是谁 | 板块阶段、轮动持续性、龙头及入选原因 | 只看当日涨幅榜 |
| 当前仓位是否合理 | 当前暴露、目标区间、集中度和回撤护栏 | 自动替用户下单或给不可追溯的仓位数字 |
| 关注股票是否具备条件 | 市场、板块、个股指标、资金和风险的联合判断 | 脱离市场环境单看某个指标 |

## 4. “主力资金”语义契约

“主力资金”不是可直接观测的单一事实。平台应分层展示，永远保留来源和局限：

| 证据层 | 示例 | 平台表述 |
|---|---|---|
| L1 上游资金流口径 | 按成交单大小估算的主力净流入 | “数据源报告的主力净流入代理值”，不是交易所认证身份 |
| L2 公开机构痕迹 | 龙虎榜、大宗交易、融资融券、公开持仓变化 | “有范围和披露时滞的机构活动证据” |
| L3 价量推断 | OBV、MFI、量价背离、筹码分布、板块扩散 | “模型推断”，不得写成实际机构买卖 |

每层至少提供：

- `1d / 5d / 20d` 净值或变化；
- 连续性、正值天数占比、标准分、集中度；
- 资金与价格背离；
- 板块内扩散度；
- `source`、`as_of_date`、计算版本、缺失原因和置信度。

硬规则：

- 成交额永远不命名为“净流入”。
- 不把不同来源和不同口径直接相加。
- 数据缺失时降低置信度，不做插值式“补结论”。
- 不用缺少可靠日期语义的排行榜构造历史。

## 5. 三个开源仓库的迁移评估

### 5.1 myhhub/stock：A 股领域能力目录

[InStock](https://github.com/myhhub/stock) 是三者中最接近本项目页面目标的 A 股一体化产品。仓库声明 Apache-2.0，覆盖日线、板块、资金流、技术指标、K 线形态、筹码、策略、回测和 Web 展示。

值得适配复用：

- [技术指标目录与计算组织](https://github.com/myhhub/stock/blob/b6e0ca2268cfbadd02f5ed052159c187b6670231/instock/core/indicator/calculate_indicator.py)：可作为本项目指标覆盖范围和字段命名的参考。
- [K 线形态目录](https://github.com/myhhub/stock/blob/b6e0ca2268cfbadd02f5ed052159c187b6670231/instock/core/pattern/pattern_recognitions.py)：适合作为后续可选信号，不应进入首期核心判断。
- [筹码分布实现](https://github.com/myhhub/stock/blob/b6e0ca2268cfbadd02f5ed052159c187b6670231/instock/core/kline/cyq.py)：可用于实验性成本分布模块，必须先用固定样本验证。
- [K 线与多指标窗格设计](https://github.com/myhhub/stock/blob/b6e0ca2268cfbadd02f5ed052159c187b6670231/instock/core/kline/visualization.py)：复用信息结构，不复用 Bokeh 服务端渲染栈。
- 日任务被拆成数据、指标、形态、策略、回测的流水线分类。
- A 股策略样例可作为策略注册表的候选规则，不可直接当成有效策略发布。

不建议迁移：

- Tornado + MySQL + Bokeh 的整套架构，与现有 FastAPI/DuckDB/Web 架构冲突。
- 东方财富当前排行类爬虫直接进入历史数据；部分接口缺少足够稳定的日期语义。
- 自动交易、券商适配、代理/Cookie 处理，超出当前产品边界。
- 仓库快照中未发现系统化测试；指标和策略代码必须通过独立金标验证。
- 第三方商业前端资源、默认数据库凭据及连接日志做法不能进入本项目。

迁移方式：`领域清单参考 + 小段适配 + 独立测试`，不 fork。

### 5.2 TradingAgents：决策工作流与证据约束

[TradingAgents](https://github.com/TauricResearch/TradingAgents) 是 Apache-2.0 的多代理研究框架，组织了基本面、情绪、新闻、技术分析、牛熊辩论、交易员和风险角色。

值得适配复用：

- [图工作流的阶段划分](https://github.com/TauricResearch/TradingAgents/blob/a33fd4c0f134485a43553a2c23a63cb14adbd88f/tradingagents/graph/setup.py)：适合映射成“市场 → 板块 → 个股 → 风险”的复盘流水线。
- [结构化输出 Schema](https://github.com/TauricResearch/TradingAgents/blob/a33fd4c0f134485a43553a2c23a63cb14adbd88f/tradingagents/agents/schemas.py)：可借鉴为市场状态、交易提议和组合决策的 Pydantic 契约。
- [确定性市场快照校验](https://github.com/TauricResearch/TradingAgents/blob/a33fd4c0f134485a43553a2c23a63cb14adbd88f/tradingagents/dataflows/market_data_validator.py)：先验证数值证据，再允许生成解释。
- [SQLite 检查点](https://github.com/TauricResearch/TradingAgents/blob/a33fd4c0f134485a43553a2c23a63cb14adbd88f/tradingagents/graph/checkpointer.py)：适合长复盘任务的恢复和审计。
- [报告树与合并报告](https://github.com/TauricResearch/TradingAgents/blob/a33fd4c0f134485a43553a2c23a63cb14adbd88f/tradingagents/reporting.py)：适合生成每日证据报告和决策日志。

不建议首期迁移：

- 整套 LangGraph、多模型和外部数据供应商依赖。
- Yahoo `.SS/.SZ` 只能提供有限的 A 股标的支持，不能代替现有本地数据层。
- LLM 输出具有非确定性，不适合作为资金、仓位和买卖信号的权威来源。
- 代理不得读取未验证原始数据，也不得拥有组合或订单写权限。

迁移方式：先实现确定性的 `EvidencePack`、结构化结论、报告树和决策日志；后期可加只读的“研究委员会”，所有数字必须引用证据包。

### 5.3 vnpy/vnpy：指标、时点数据、因子与回测

[VeighNa](https://github.com/vnpy/vnpy) 是 MIT 许可的成熟量化交易框架。其核心更偏实时事件驱动、桌面交易和交易网关，但 `ArrayManager` 与 `vnpy.alpha` 对本项目的研究层有参考价值。

值得适配复用：

- [`ArrayManager` 指标接口](https://github.com/vnpy/vnpy/blob/1b78494979deb4c4996f6b864f234d9839f2f239/vnpy/trader/utility.py)：可参考其 TA-Lib 封装和指标注册方式。
- [`AlphaLab`](https://github.com/vnpy/vnpy/blob/1b78494979deb4c4996f6b864f234d9839f2f239/vnpy/alpha/lab.py)：研究数据、模型、信号和回测的流程组织。
- [因子数据集模板](https://github.com/vnpy/vnpy/blob/1b78494979deb4c4996f6b864f234d9839f2f239/vnpy/alpha/dataset/template.py)：因子表达式、数据处理和训练/验证/测试切分。
- [组合回测指标](https://github.com/vnpy/vnpy/blob/1b78494979deb4c4996f6b864f234d9839f2f239/vnpy/alpha/strategy/backtesting.py)：收益、换手、佣金、最大回撤和 Sharpe 等评估维度。
- 指数成分历史的时点化设计，能避免使用今天的成分回测过去。

不建议迁移：

- 事件引擎、交易接口、风控下单和实时行情基础设施。
- [PySide6/pyqtgraph 桌面图表](https://github.com/vnpy/vnpy/blob/1b78494979deb4c4996f6b864f234d9839f2f239/vnpy/chart/widget.py)，无法直接用于 Web。
- 在首期引入完整 `vnpy.alpha`、LightGBM/MLP 等机器学习栈；当前最先缺的是可信的市场和板块派生数据。

迁移方式：首期仅适配指标接口和回测语义；成熟后再把 `vnpy.alpha` 作为隔离的研究实验层评估。

### 5.4 复用决策矩阵

| 能力 | 来源 | 决策 | 进入阶段 |
|---|---|---|---|
| 基础技术指标 | InStock + VeighNa + TA-Lib | 自有适配层调用成熟库 | Release 0 |
| Web K 线 | KLineChart | 直接依赖并封装 | Release 0 |
| A 股指标/形态/策略目录 | InStock | 参考并逐项验证 | Release 0–3 |
| 筹码分布 | InStock | 实验性适配 | Release 3 以后 |
| EvidencePack / 报告树 / 检查点 | TradingAgents | 复用设计 | Release 2 |
| 多角色 LLM 研究 | TradingAgents | 延后、只读 | Later |
| 时点化成分股与因子数据集 | VeighNa Alpha | 复用设计 | Release 1/3 |
| 组合回测统计 | VeighNa Alpha | 适配语义 | Release 3 |
| 券商、事件引擎、自动交易 | VeighNa/InStock | 明确不引入 | 不在路线图 |

如复制上游源代码而非仅参考接口和设计，必须记录来源提交并保留 Apache-2.0 或 MIT 的许可与声明。

## 6. 推荐的目标架构

### 6.1 保留

- BaoStock 无复权 OHLCV + `adjust_factor`；
- DuckDB/Parquet 规范行情和派生快照；
- SQLite 本地持仓、自选、策略、提醒和决策日志；
- FastAPI 服务边界；
- LaunchAgent 盘后调度；
- `as_of_date`、交易日、数据覆盖率、质量门禁和无未来数据规则。

### 6.2 新增派生数据产品

所有数据集均需包含 `as_of_date`、`computed_at`、`source_version`、`formula_version` 和质量状态：

1. `security_master_history`：证券、交易板、上市/退市状态。
2. `index_component_history`：指数成分的有效期历史。
3. `sector_membership_history`：行业/概念分类及有效期。
4. `indicator_series`：个股和指数指标序列。
5. `sector_daily_snapshot`：板块收益、宽度、流动性、相对强度和资金证据。
6. `fund_flow_evidence`：按 L1/L2/L3 分层的市场、板块和个股证据。
7. `market_regime_snapshot`：市场状态、风险偏好、置信度和解释。
8. `portfolio_daily_snapshot`：净值、现金、仓位、集中度、风险预算和回撤。
9. `evidence_pack` / `review_report`：每日可重放的复盘输入与输出。

### 6.3 API 产品面

- `GET /analysis/market-regime`
- `GET /sectors`
- `GET /sectors/{sector_id}`
- `GET /securities/{symbol}/analysis`
- `GET /portfolio/risk`
- `GET /reviews/{trade_date}`

前端不自行计算指标或猜测数据状态，只展示后端已确认、可追溯的结果。

### 6.4 前端路线

- 将当前单页脚本按市场、板块、个股、组合、复盘报告拆成 Vite + TypeScript 模块。
- 不预设必须迁移到 React；先用模块化 TypeScript 和组件封装完成垂直切片。
- 首页按决策顺序组织：市场状态 → 资金证据 → 板块轮动 → 持仓风险 → 关注标的。
- 个股页将市场状态、所属板块、龙头地位、资金证据和技术图表放在同一上下文中。

## 7. 核心模型定义

### 7.1 市场状态模型

每日生成两个层级：

- 战略状态：`bull / range / bear`
- 战术状态：`risk_on / neutral / risk_off`

输入维度：

1. 趋势：主要指数相对 MA20/60/120、均线斜率。
2. 宽度：上涨/下跌、站上 MA20/60 比例、新高/新低。
3. 流动性与资金：成交额趋势和可用的资金证据。
4. 风险：波动、回撤、横截面离散度。
5. 领导力：强势板块持续性和龙头扩散。

输出必须包含分项得分、总分、置信度、缺失输入、支持证据和反例。模型公式版本化，阈值可以回放。

在声称“全 A 股市场状态”前，股票池至少覆盖沪深各交易板，指数应补充上证、深证、沪深 300、中证 500/1000、创业板等代表序列；北交所是否纳入需单独确认和标注。

### 7.2 板块轮动与龙头

板块状态不能只取当日涨幅，至少结合：

- `5d / 20d / 60d` 相对强度；
- 上涨扩散度、站上均线比例；
- 成交额变化与集中度；
- L1/L2/L3 资金证据及持续性；
- 龙头数量、龙头持续天数和板块内部离散度。

龙头候选需同时满足可交易性、相对强度、成交活跃度、趋势质量和板块贡献，并展示各项原因。避免把一字板、停牌、流动性异常标的直接排在可操作候选首位。

### 7.3 个股技术驾驶舱

首期默认展示：

- 前复权日 K、成交量；
- MA5/10/20/60/120/250；
- MACD、RSI、KDJ、BOLL、ATR；
- OBV、MFI、量比；
- 市场状态、板块阶段、板块排名/龙头状态；
- 资金证据和风险提示。

指标可配置，但首期不追求一次性覆盖所有 InStock 指标。每个指标要有公式、参数、暖机期和金标样本。

### 7.4 仓位与风险

只提供本地、只读式决策辅助：

- 现金、净值和每日组合快照；
- 单股/板块集中度；
- ATR 风险单位；
- 最大单股、最大板块、总风险预算；
- 当前仓位与目标暴露区间；
- 回撤和风险状态护栏；
- 调整原因及依赖证据。

平台不连接券商、不生成订单、不自动执行。缺失成本价或现金数据时明确降级，不猜测。

## 8. 优先级

当前缺少稳定使用量和用户分层数据，不适合使用依赖 Reach 的 RICE。采用 ICE（Impact × Confidence × Ease）并用数据依赖覆盖纯分数排序：

| Epic | I | C | E | ICE | 决策 |
|---|---:|---:|---:|---:|---|
| E0 决策契约与信息架构 | 5 | 5 | 4 | 100 | Now |
| E1 指标服务与个股驾驶舱 | 5 | 5 | 4 | 100 | Now |
| E2 派生数据血缘与质量门禁 | 5 | 5 | 3 | 75 | Now |
| E6 市场状态引擎 | 5 | 4 | 3 | 60 | Next |
| E3 市场范围/证券主数据/指数扩展 | 5 | 5 | 2 | 50 | 依赖型 Now |
| E10 每日证据报告与决策日志 | 4 | 4 | 3 | 48 | Next |
| E4 板块分类历史 | 5 | 3 | 3 | 45 | 依赖型 Now |
| E8 组合台账与仓位风险 | 5 | 4 | 2 | 40 | Next |
| E9 策略回放与回测 | 4 | 4 | 2 | 32 | Later |
| E5 资金证据管道 | 5 | 3 | 2 | 30 | 战略必做 |
| E7 板块轮动与龙头 | 5 | 3 | 2 | 30 | 依赖 E4/E5 |
| E11 只读 AI 研究委员会 | 3 | 2 | 1 | 6 | Later |
| E12 高级因子/机器学习实验 | 3 | 1 | 1 | 3 | Later |

E3、E4、E5 虽然 Ease 较低，仍是市场、板块和资金结论的前置依赖，不能被低成本 UI 工作挤出路线图。

## 9. 分阶段 Roadmap

估时假设：一名主工程人员，复用现有后端；每个 Release 完成后再根据真实数据质量重估。

### Release 0：从空框架到可用的个股复盘（第 0–2 周）

目标：用户不离开平台即可完成关注股票的基础技术复盘。

范围：

- E0：确定首页和个股页的决策信息架构。
- E1：后端指标注册表、参数/暖机期/版本契约。
- E1：接入 KLineChart，完成 K 线、成交量、MA、MACD、RSI。
- E1：为自选和持仓提供个股详情入口。
- E2：每张图展示来源、`as_of_date`、复权口径、公式版本和质量状态。

验收：

- 从首页或自选在两次点击内进入个股页。
- 260 个交易日缓存数据的个股页 P95 响应目标小于 500 ms。
- 指标与 TA-Lib 固定金标在声明容差内一致。
- 暖机数据不足、停牌和缺失值均显式展示，零伪造值。
- 用户能在 60 秒内回答“趋势、动量、波动和量价是否配合”。

### Release 1：市场状态、板块结构与龙头（第 3–6 周）

目标：回答“市场处于什么状态、强势板块是谁、领导力是否持续”。

范围：

- E3：扩展证券主数据、交易板和代表性指数。
- E4：发布有有效期的行业分类和成员历史。
- E6：市场状态 v1，输出战略/战术状态、分项得分和置信度。
- E7：先基于价格、宽度、流动性和持续性形成板块轮动与龙头 v1。
- 首页形成市场 → 板块 → 个股的下钻路径。

验收：

- 页面明确显示实际覆盖市场，不用主板数据代称全 A 股。
- 合格股票的行业映射率目标不低于 95%，剩余缺口可审计。
- 每个数据就绪交易日都生成可重放的市场状态。
- 每个板块/龙头排名都能展开看到原因和原始指标。
- 历史重放使用当时有效的成分关系，无未来数据。

### Release 2：资金证据与仓位决策（第 7–12 周）

目标：回答“资金在向哪里持续移动、当前组合暴露是否匹配市场风险”。

范围：

- E5：资金源可用性探针、日期语义验证和小范围 canary。
- E5：累计不少于 20 个连续交易日的 L1/L2/L3 证据再发布趋势结论。
- E7：将合格资金证据加入板块轮动和龙头模型。
- E8：组合每日台账、现金/净值、集中度、ATR 风险预算和暴露区间。
- E10：生成每日 EvidencePack、复盘报告和决策日志。

验收：

- 每条资金结论均有来源、日期、口径层级和置信度。
- 零“用成交额冒充资金净流入”的字段或文案。
- 数据源故障时保持最后可信日期并显式降级，不发布新趋势。
- 同一输入可重复得到相同的风险指标和目标暴露区间。
- 每个仓位提示都能追溯到市场、板块、个股或组合约束。

### Release 3：策略验证闭环（第 13–18 周）

目标：把观察和规则变成可重放、可证伪的策略，而不是更多未经验证的指标。

范围：

- E9：扩展指标和策略注册表。
- E9：按日事件回放、信号记录、组合回测。
- E9：纳入 A 股 T+1、涨跌停、停牌、佣金/印花税和可交易性约束。
- E9：输出年化收益、最大回撤、Sharpe、胜率、换手和成本敏感性。
- E9：滚动训练/验证或样本外检验；保持时点化板块/指数成分。
- E10：记录“当时证据 → 当时判断 → 后续结果”，支持复盘模型误差。

验收：

- 所有信号可以按 `as_of_date` 重放。
- 自动化测试证明策略读取不会越过当日。
- 回测包含交易成本、可交易性和成分历史。
- 策略上线到观察列表前必须有样本外结果和失败条件。

### Later：增强研究，而非替代证据

- E11：引入 TradingAgents 风格的只读研究委员会，只消费 EvidencePack。
- E12：在隔离研究环境评估 `vnpy.alpha` 的因子和模型流程。
- 经过金标验证后再增加筹码分布和 K 线形态。
- 根据实际使用决定通知、跨设备和更多数据供应商。

## 10. 首轮低成本验证

在大规模开发前完成五个短实验：

1. 选 5 只不同状态股票做个股驾驶舱，校验指标和信息密度。
2. 连续 10 个交易日手工生成 EvidencePack，记录回答五个核心问题所需时间。
3. 对市场和 3–5 个板块做资金数据 canary，验证日期、历史连续性和口径漂移。
4. 用至少 20 个历史日期回放市场状态，与用户当日判断对照并记录分歧。
5. 用合成组合验证仓位/风险页，不触碰真实券商或产生订单。

## 11. 成功指标

北极星指标：

- 收盘数据就绪后，完成一次证据充分的复盘用时小于 5 分钟。

质量与任务指标：

- 100% 展示型结论包含来源、日期、公式/模型版本。
- 100% 资金流结果标明证据层级和口径。
- 过期、部分或缺失数据被静默使用的次数为 0。
- 个股指标金标通过率 100%。
- 合格股票的板块覆盖率不低于 95%。
- 市场状态在每个“数据就绪”交易日可用且可重放。
- 可用性测试中，五个核心决策问题均能在不离开平台的情况下回答。
- 同一组合输入的仓位和风险结果可重复率 100%。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 免费资金流接口不稳定或日期语义不足 | 无法可信回答主力资金 | canary、来源分层、缓存最后可信日；必要时评估付费/替代源 |
| “主力”被误解为可识别的机构身份 | 产生过度确信 | 固化 L1/L2/L3 语义和 UI 标签 |
| 只扩 UI，不补派生数据 | 页面漂亮但无法决策 | 每个页面必须绑定可验收的数据产品 |
| 指标过多导致噪声 | 降低复盘效率 | 默认最小指标集，其他按需开启 |
| 市场覆盖不足 | 牛熊结论失真 | 先扩展股票池和指数，再升级结论范围 |
| 历史分类使用当前成员 | 回测产生幸存者偏差 | 有效期建模、时点读取、无未来测试 |
| 过早引入 LLM/ML | 不确定性和维护成本上升 | EvidencePack 稳定后再做只读增强 |
| 整体 fork 上游项目 | 架构冲突和升级负担 | 维护模块级来源清单和适配边界 |

## 13. 明确不在本 Roadmap 中

- 分钟/Tick 实时交易终端；
- 券商账户、自动交易或订单执行；
- 由 LLM 直接给出权威买卖点和仓位；
- 把单一第三方“主力净流入”当作真实机构身份；
- 整体替换成 InStock、TradingAgents 或 VeighNa；
- 在数据和策略验证前堆叠大量 AI 模型。

## 14. 待确认假设

1. 产品继续坚持盘后、本地优先、无券商、无自动交易。
2. “全 A 股”首阶段至少包括沪深各交易板；北交所是否纳入单独决定。
3. 可以使用第三方大单口径，但必须明确称为代理值并展示来源。
4. 前端优先采用 Vite + TypeScript + KLineChart，不先做全量框架重写。
5. 首轮估时按一名主工程人员计算。
6. 当前约一年的历史窗口需要扩展；可靠市场状态和策略验证建议至少覆盖 500 个交易日，并继续向多个市场周期扩展。
7. AI 只在确定性证据层稳定后进入，并保持只读。

## 15. 决策门

进入实现前需要确认：

- 是否批准“保留现有后端 + 模块级复用”的推荐路线；
- “全 A 股”是否在 Release 1 纳入北交所；
- 是否接受 L1 上游大单口径作为带标签的代理证据；
- Release 0 是否只对持仓/自选做垂直切片，再扩展到全市场；
- 市场状态模型的首版权重是否先由规则设定，再用历史回放校准。
